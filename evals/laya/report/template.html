Bottom line. OpenJev is the only one of the two that does jevgrep's job. It needs a GPU server to be practical. Laya is fast and fine for picking among a handful of tools, but on this benchmark it did no better than keyword search, and it cannot judge source code.

No Jev API key was used. "Jev" figures come from a run recorded in the jevgrep repository. All tests ran on an Apple M3 Max (36 GB).

Background

Where the decision model sits

Jev, Laya and OpenJev are decision models: they do not write text. You give them a situation and a question, and they return a probability (yes/no) or a ranked choice. Both jobs below use that one skill.

a · Finding code with jevgrep

Question"Where is the Content-Length header set for GET requests?"

The whole value is in step 1: a small packet saves the coding agent's tokens. A model that says "yes" to everything turns the packet into a dump of the repository.

Use case a · finding code

Laya keeps everything. OpenJev keeps the right files.

Each file was scored with jevgrep's own question: "does this file help investigate the requested behaviour?" jevgrep keeps a file when the score is above 0.25.

Laya kept 186 of the 187 unrelated files, so it filters nothing. OpenJev kept 85% of the files the fix or its tests changed and only 13% of files in the same folders and 2% of random files. The 4 fix files it missed were secondary ones: two Django database backends, a pytest test file and a pylint constants file.

Is it consistent across projects?

AUC is the chance that a random fix file scores higher than a random other file. 0.5 is a coin flip. OpenJev scores 0.95 or higher on 8 of 10 projects and at least 0.77 on all of them. Laya ranges from 0.33 to 0.75, close to a coin flip (pooled against same-folder files: {{laya_auc_sib}} for Laya, {{oj_auc_sib}} for OpenJev).

How to read this

  • Top 3 is the number that matters for shortlisting. If the right tool is in the top 3, the LLM can still pick it.
  • {{tools_reading}}
  • Laya squeezes the tool list. It fits all 20 options into 192 tokens (English checkpoint), so each tool keeps only about 8 tokens of its name and description. That limits it once tools get similar or numerous. Laya's own documentation recommends its shortlist mode above about 20 options.
  • This benchmark is easy for keywords. The requests share many words with the tool descriptions, which is why BM25 does so well. Requests worded differently from the tool descriptions would favour the model that understands meaning.

Recommendation

  • Code search (a): use OpenJev on a GPU server: vLLM on one 80 GB NVIDIA GPU, or a 24 GB card with the GGUF build. The Mac is fine for testing but too slow for daily use. Check the licence before commercial use.
  • Tool picking (b): {{rec_tools}}
  • Do not use Laya for code search. It is trained on tickets and email, not source code.

Limits of these results

  • Retrieval quality only. jevgrep's own acceptance test, a coding agent solving the bug at lower cost, was not run.
  • The full search was run on one bug for OpenJev and two bugs for Laya.
  • OpenJev ran as the 4-bit build (about 0.6 points below the full model on its own benchmark).
  • Tool test: one correct tool per request and 20 tools per request, on one public benchmark.
  • "Jev" figures come from an earlier recorded run, not a paired live run.
